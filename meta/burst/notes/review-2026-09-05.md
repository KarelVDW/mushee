## packages/notation/src/model/util/AccidentalMinimizer.ts + Score.minimizeAccidentals (T1: sounding-pitch key ranking, dropping latent mid-bar key restatements) — commit e384895

**Verdict:** Safe to keep on experimental: dropping restatements only removes keys that are already invisible/unserialized (setKeySignature's own redundancy rule), and sounding-basis ranking removes the spelling feedback loop; the one finding is a low-severity ranking inaccuracy for cross-region ties, not a meaning change (time box hit at 10:00 before further adversarial probing could be run).

- **low** `packages/notation/src/model/util/AccidentalMinimizer.ts:98` — Under basis 'sounding', a tie continuation whose predecessor lies outside the walked region is auditioned with every enharmonic spelling free, but the actual respell (basis 'spelling') then forces the predecessor's written pitch — so the audition's drawnCount can undercount the accidentals the chosen key will really draw for cross-region ties.
    - Evidence: candidatesFor: `if (this.basis === 'spelling') return [previous.pitch]` is skipped for 'sounding' and falls through to `Pitch.spellingsOf(pitch.toMidi())`; Score.minimizeAccidentals ranks keys solely via `drawnUnder(...)` with 'sounding', then respells with the default 'spelling' basis. A region starting on a tie continuation (e.g. Ab tied from the prior bar into a region auditioned in E major) counts 0 for that note under the audition while the respell must write Ab/G# per the predecessor, drawing an accidental. Idempotency is preserved (audition ignores spellings both passes), so this is a ranking inaccuracy, not a meaning change — not exercised in a test within the time box.
    - Fix: In the 'sounding' audition, treat an out-of-walk tie predecessor as a fixed sounding constraint: return the predecessor's pitch class spellings only (or return [previous.pitch] when the predecessor is not itself in the current key region), so the count matches what the respell will write.

- **medium** `apps/api/src/recordings/pipeline/recording-pipeline.ts:713` — Race: on the normal end-message-then-close path, close() persists audioKey = null even though the upload succeeds, because the second pipeline.finalize() returns before the first one's archiver.finalize() has completed.
    - Evidence: RecordingSession.finalize() (recording-session.ts:141) fires `void this.pipeline.finalize()` without awaiting. RecordingPipeline.archive() (recording-pipeline.ts:713-715) sets `this.archived = true` synchronously and returns immediately on any subsequent call, without awaiting the in-flight first call. So when RecordingSession.close() (recording-session.ts:154) does `await this.pipeline.finalize()`, that resolves as soon as kick() finishes, while the first call is still inside `await finished(this.audioStream)` in RecordingArchiver.finalize() (recording-archiver.ts:76). `archivedAudioKey` (recording-archiver.ts:39) gates on `audioArchived`, which is only set after `finished()` resolves (line 77), so close() reads null and writes `audioKey: null` (recording-session.ts:163). Not a data-loss bug (discoverAudioKey fallback in recordings.service.ts:145 still finds the object), but the feature is silently ineffective on the common path.
    - Fix: Make archive() await the in-flight promise instead of short-circuiting: `private archivePromise: Promise<void> | null = null; private archive() { if (!this.archiver) return Promise.resolve(); this.archivePromise ??= this.doArchive(); return this.archivePromise }` (move the current body to doArchive).
